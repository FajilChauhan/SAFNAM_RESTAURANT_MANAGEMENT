# dashboard

Production dashboard aggregation APIs for the single SAFNAM Restaurant operation.

This module is read-only. It does not create dashboard tables, analytics snapshots, branch filters, tenant filters, or duplicate business state.

## Folder Structure

- `dashboard.controller.ts` - validates request query params and returns API responses.
- `dashboard.service.ts` - role payload composition, quick actions, and derived capability metadata.
- `dashboard.repository.ts` - optimized PostgreSQL aggregation queries over existing business tables.
- `dashboard.routes.ts` - authenticated role-based dashboard routes.
- `dashboard.dto.ts` - strict dashboard DTO and payload types.
- `dashboard.validator.ts` - Zod dashboard query validation.

## API Design

- `GET /dashboard/customer`
  - Role: `CUSTOMER`
  - Aggregates current active booking, table, room, cart, orders, invoice, payment status, booking history, recent orders, favourite foods, visit count, spending, leaderboard position, offers, rewards, notifications, feedback, and customer quick actions.
- `GET /dashboard/reception`
  - Roles: `ADMIN`, `MANAGER`, `RECEPTION`
  - Aggregates today's bookings, walk-ins, check-ins, checkouts, table/room availability, pending payments, pending invoices, current customers, recent activities, and reception quick actions.
- `GET /dashboard/kitchen`
  - Roles: `ADMIN`, `MANAGER`, `KITCHEN`
  - Aggregates kitchen queue by status, priority orders, average preparation time, today's orders, kitchen statistics, and kitchen quick actions.
- `GET /dashboard/manager`
  - Roles: `ADMIN`, `MANAGER`
  - Aggregates daily operations: revenue, orders, bookings, customers, occupied tables/rooms, kitchen queue count, pending payments, top foods/categories, customer statistics, recent records, current offers, low availability menu items, dashboard statistics, and manager quick actions.
- `GET /dashboard/admin`
  - Role: `ADMIN`
  - Includes the full Manager dashboard plus employee counts, user/role/permission statistics, system/database health, storage config summary, audit contract summary, restaurant settings, tax summary, notification/game/loyalty summaries, employee activity, and admin quick actions.

Optional query params:

- `listLimit` - widget list size, default `10`, max `50`.
- `historyLimit` - customer history size, default `10`, max `100`.

## Repository Design

`DashboardRepository` owns read-only aggregation methods:

- `customer(customerId, query)`
- `reception(query)`
- `kitchen(query)`
- `manager(query)`
- `adminSystem()`

Each method returns one dashboard-shaped row generated by PostgreSQL JSON aggregation. The Admin service composes Manager plus Admin system data using `Promise.all()` so configuration-heavy and operations-heavy reads run independently.

## Aggregation Strategy

- Customer dashboard aggregates from bookings, tables, rooms, carts, cart items, orders, kitchen queue, invoices, payments, checkout sessions, order items, offers, game rewards, notifications, and feedback.
- Reception dashboard aggregates from bookings, users, tables, rooms, invoices, payments, and checkout sessions.
- Kitchen dashboard aggregates from kitchen queue, orders, bookings, customers, tables, and rooms.
- Manager dashboard aggregates from payments, orders, bookings, users, kitchen queue, order items, menu items, categories, feedback, offers, tables, rooms, and invoices.
- Admin dashboard aggregates from Manager data plus users, restaurant settings, invoices/tax fields, notifications, offers, rewards, static operation permissions, and storage runtime configuration.

## Performance Optimization

- One HTTP call loads one dashboard.
- Repository queries use PostgreSQL-side `jsonb_agg`, `jsonb_build_object`, `COUNT`, `SUM`, `AVG`, and bounded subqueries.
- Dashboard lists are capped by validated limits.
- Existing indexed fields are used for date, status, customer, booking, order, payment, and queue filters.
- No analytics tables are written and no business rules are duplicated.
- Role-specific endpoints avoid exposing customer or restaurant selector parameters.

## Future Redis Strategy

- Customer: per-user cache key, short TTL, invalidate on booking, cart, order, invoice, payment, reward, notification, or feedback changes.
- Reception: operational cache with very short TTL, invalidate on booking/check-in/checkout/table/room/payment changes.
- Kitchen: queue cache or socket-published snapshot, invalidate on order and kitchen queue status/priority changes.
- Manager: minute-level cache for top foods/categories and daily statistics, invalidate on payment/order/booking/menu/feedback changes.
- Admin: separate cache for system/config summaries and manager dashboard data; invalidate users/settings/permissions independently from operational metrics.
